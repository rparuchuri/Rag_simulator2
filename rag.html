Step 1 — Documents & Chunking
Knowledge Base — Your Documents
These are the documents your RAG system will learn from. Click a document to see how it's split into chunks.
📘 RAG Overview
Retrieval Augmented Generation is a technique that enhances LLMs with external knowledge at inference time.
📗 Vector Databases
Vector databases store embeddings — high-dimensional numerical representations of text — and enable semantic search.
📙 LLM Limitations
Large Language Models have a knowledge cutoff and cannot access private or proprietary data without external retrieval.
📕 Chunking Strategy
Chunking splits documents into smaller pieces. Chunk size, overlap, and splitting method affect retrieval quality significantly.
Chunks from selected document
← Select a document above to see its chunks
Why chunking matters: LLMs have a context window limit. Breaking documents into chunks (typically 200–500 tokens) lets you retrieve only the most relevant pieces rather than stuffing the entire document into the prompt. Chunk overlap (e.g. 50 tokens) prevents context from being cut off at chunk boundaries.
Text → Embedding Conversion
An embedding model converts text into a high-dimensional numerical vector. Similar text produces similar vectors — this is how semantic search works.
Input text (chunk example)
Embedding vector (1536 dimensions — visualized as 128)
Numeric values (first 8 dimensions shown)
What just happened: The embedding model (e.g. text-embedding-ada-002) converted your text into a 1536-dimensional vector. Each number represents a semantic feature. Two chunks about "dogs" will have similar vectors; a chunk about "quantum physics" will be far away in vector space.
Vector Database — Pinecone / pgvector / Chroma
All chunk embeddings are stored in the vector database. Each entry contains the vector, the original text, and metadata.

How it's stored: The vector database uses an index (like HNSW or IVF) to organize vectors for fast approximate nearest neighbor search. When a query arrives, it finds vectors that are closest in distance (cosine similarity or dot product), not just keyword matches. This enables semantic search — finding meaning, not just words.
User Query
Query embedding vs stored chunks (cosine similarity)
Top-3 retrieved chunks K=3
K-Nearest Neighbor search: Your query is embedded into the same vector space as your documents. The database returns the top-K most similar vectors (here K=3). Only these chunks — not the full document — are passed to the LLM, keeping the context window focused and efficient.
Prompt Engineering — Injecting Retrieved Context
The retrieved chunks are injected into a structured prompt. This is the "Augmented" part of RAG.
🤖 System Prompt
📚 Retrieved Context (injected)
💬 User Query
Why this works: The LLM now has grounding context it never saw during training. It's instructed to answer based only on provided context, reducing hallucination. The model doesn't need to "know" the answer — it needs to read and synthesize the retrieved chunks.
LLM Generation — Grounded Response
The LLM reads the augmented prompt and generates an answer grounded in your retrieved context — not hallucinated from its training weights.
Sources used
The full RAG loop is complete. The answer was grounded in retrieved chunks, not hallucinated. If you add new documents to the vector DB, the LLM can answer questions about them immediately — no retraining needed. This is the core power of RAG: dynamic knowledge without touching model weights.
🎉 You've completed the RAG pipeline!
Query → Embed → Search DB → Retrieve Top-K → Augment Prompt → Generate. This is exactly what Notion AI, Atlassian Intelligence, and thousands of RAG applications do on every user request.
